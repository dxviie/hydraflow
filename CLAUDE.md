# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview
hydraflow is a browser-based, node-based editor for the hydra video synth (`hydra-synth`), built with Svelte 5 and Svelte Flow (`@xyflow/svelte`), bundled by Vite, with Bun for installing, scripts and tests. It is a sibling of HYDRACTRL (github.com/dxviie/HYDRACTRL) and shares its look: the HYDRACTRL site's tokens and fonts (`src/app.css`), square corners, text and nodes in near-black boxes over the visuals, violet for selection, green for run.

The site is two pages, built together by Vite (`vite.config.ts`): the landing page at `/` (`index.html`, `src/site/`) and the editor at `/app` (`app.html`, `src/main.ts`, `src/App.svelte`). Links that open a patch go to `/app#patch=…`; the landing page forwards old `/#patch=…` links there. In the editor the output plays fullscreen behind the patch; nodes follow "direction A" of the design session: a node shows its main parameters at rest, everything when selected, and one line of code when folded; the live preview is a per-node toggle.

- `src/lib/graph/` is the patch, with no browser or Svelte in it, and is where logic belongs when it can live there: `types.ts`, `compile.ts` (patch to expressions, to hydra code with `toCode`, to hydra chain objects with `buildChain`; `signature` is everything that needs new shaders), `params.ts` (what a driven parameter is worth, and the same thing as hydra code: a test keeps the two equal, against hydra's own array sequencing), `audio.ts` (how the sound becomes `a.fft`: the settings a patch holds, under hydra's names, and `Bands`, hydra's arithmetic without per-frame arrays; a test keeps it equal to hydra's own `lib/audio.js`), `edit.ts` (wiring changes), `storage.ts` (the saved format, parsed piece by piece, and the starter patch), `history.ts` (undo).
- `src/lib/hydra/catalog.ts` builds the node catalog from hydra's own `glsl-functions.js` and adds ranges, primary parameter counts and descriptions; a test fails when hydra ships a texture function the catalog has no node for. `engine.ts` owns the hydra instance, the render loop, the inputs, the listener and the per-node previews (drawn with hydra's regl into one small framebuffer, read back a few times a second; the rows come back in the order hydra shows them on screen, so the preview canvas is not flipped). `inputs.ts` opens a camera, a screen, a picture or a video as an element hydra reads. `audio.ts` listens: hydra only ever opens the system's default microphone, so its own audio stays off (`detectAudio: false`) and `Listener` opens the input the person chose (found again by its label when its id changed, the system default standing in while it isn't connected), reads it with the analyser hydra uses (Meyda's loudness, set up as hydra sets it up) and feeds `Bands` once a frame. It starts the first time something listens: the patch, the visualiser, or the panel's `listen`.
- Input nodes (`cam`, `screen`, `image`, `video`: a `source` in the catalog) take hydra's inputs s0 to s3 in patch order; a fifth gets none. The engine keeps what each one holds open by node (`Engine.held`), not by input, so a camera or a shared screen survives the inputs shifting. A screen is only shared from a click (`Engine.startScreen`). Pictures and videos live in IndexedDB (`src/lib/media.ts`); the patch holds their id and name only, and files no saved patch names are pruned at start-up.
- Control nodes (`lfo`, `audio`: a `control` in the catalog) make a number instead of a picture. Their wires go into parameters: an edge's `input` is `in`, `by` or `p:<parameter>` (`paramInput`, `inputParam` in `types.ts`). `fits` in `storage.ts` is the one rule for what can be wired where, used by the parser and by the editor. A control node is a drive with a place of its own (`controlDrive` in `params.ts`), so its number and its code come from the same tested functions as the `~` drives. `controlsOf` in `compile.ts` names them (`lfo`, `lfo2`, `audio`); in exported code each is `var <name> = () => …` at the top (`var`, because hydra's editor runs a sketch again in the same global scope, where `const` would fail), and a wired parameter is written as that name. The engine keeps each control's drive in `Engine.controls`, rebuilt on change, never per frame.
- Sound has two kinds of settings. How it is read (`bins`, `cutoff`, `smooth`, `scale`: `AudioSettings`) belongs to the patch: saved as `audio` only when it isn't hydra's own, so older patches save back unchanged, and written into exported code as `a.setBins(6)`… when the sketch listens. An audio node or drive on a band the patch doesn't have moves to the last one (`withinBands` in `storage.ts`, the one rule for the parser and the editor). What is listened to and whether the visualiser shows belong to the browser (`hydraflow.audio` in local storage, `AudioPrefs`): a patch never carries a device's name.
- What plays behind the editor is `Shown`: an output, or `"all"` for hydra's four quarters, which is `render()` in exported code.
- `src/lib/share.ts` packs a saved patch into the address's `#patch=…` (deflated, base64url, size-capped both ways) and reads one back through `parsePatch`. Opening a link sets the person's own patch aside under `hydraflow.patch.mine` and offers it back in the status line; never replace their patch without that.
- `src/lib/flow.ts` converts between the patch and Svelte Flow's nodes and edges, which are the patch while the editor is open. A saved patch must save back as the same string (a test checks it): undo relies on that.
- `src/site/` is the landing page, for people who have never touched hydra: plain HTML in `index.html` that reads without JavaScript, styled by `landing.css`, and `landing.ts`, which plays the hero's patch (`hero.ts`) behind the page on the editor's own `Engine`, lets its numbers be dragged with `scrub.ts`, shows it as code with `toCode` and links it into the editor with `share.ts`. `hero.test.ts` keeps the page's static markup (its rows, its values, its code) equal to the patch. Every section is a node: a category colour on top, sockets, a wire down to the next.
- The logo (`public/logo.svg`, one colour, used as a CSS mask; `public/logo-color.svg` in the category colours; `public/favicon.svg` on a dark tile, with PNGs rendered from it) is a node whose three wires grew heads: HYDRACTRL's hydra, made friendly. `public/site/hydractrl-logo.svg` is HYDRACTRL's own mark, for the link to it.
- `src/lib/ui/` holds the components: `Editor.svelte` (the shell: Svelte Flow, palette requests, connect and delete rules, undo, autosave, dropped files, links, notices, keys; nodes reach it through the `EDITOR` context), `HydraNode.svelte` (the one node type for every catalog entry), `SourceRows.svelte` (what an input node shows: its file, its screen, what went wrong), `Scope.svelte` (a control node's number as a moving trace), `AudioPanel.svelte` (the audio settings under the top bar: the input, the four settings as rows, the visualiser's switch; closed, only the visualiser stays) and `Spectrum.svelte` (the visualiser: the bands against the cutoff and scale lines), `ParamRow.svelte` (which carries the parameter's socket; `plain`, it is also a row outside a node), `DrivePanel.svelte`, `NumberField.svelte`, `Palette.svelte`, `TopBar.svelte`, `StatusBar.svelte` (which also carries notices), `CodePane.svelte`, and `scrub.ts` (drag sideways to change a number).

Rules that hold the design together:
- Parameters reach hydra as functions it calls every frame (`Engine.chainOf`), so a value change never recompiles a shader. Only a change of `signature` calls `Engine.apply`.
- A patch is data: nothing in it is evaluated as code, and it never makes the browser fetch anything (files are the person's own, named, not linked). Keep it that way (no `eval`, no `new Function` outside tests, no URLs in a patch), so opening someone else's patch stays safe.
- An input holds one wire; a wire that would close a loop is refused (feedback goes through a `src` node); deleting a node closes the gap in its chain.
- A control wired into a parameter wins over the parameter's own value and `~` drive, which come back when the wire goes. A control's own settings are plain numbers: nothing drives the driver.
- Svelte Flow: use only what the MIT package exports. Never set `proOptions.hideAttribution`, and never copy code from Svelte Flow's Pro examples.
- Drags go through pointer events (`scrub.ts`), never mouse events, so touch works.

## Build Commands
- Setup: `bun install`
- Start dev: `bun dev`
- Build: `bun run build` (static site into `dist/`: `index.html` is the landing page, `app.html` the editor, which the host serves at `/app`)
- Preview the build: `bun run preview`
- Lint: `bun run lint` (Biome, `src/`)
- Format: `bun run format`
- Type-check: `bun run check` (svelte-check; it needs TypeScript 6, not 7)
- Test all: `bun test`
- Test single: `bun test src/path/to/file.test.ts` or `bun test -t "test description"`

## Code Style Guidelines
- **Formatting**: Follow the Biome config (2-space indent, 100 char line length); Svelte script blocks stay indented
- **Svelte**: Svelte 5 runes (`$state`, `$derived`, `$effect`, `$props`); nodes and edges are `$state.raw` arrays bound to `<SvelteFlow>`, replaced rather than mutated
- **Types**: TypeScript with strict mode; avoid `any` (hydra's untyped chain objects are the one exception, as `Chain`)
- **Naming**: camelCase for variables/functions, PascalCase for classes and components
- **Tests**: `bun test`, next to the code as `*.test.ts`; test names say what the code does for the person using it
- **Performance**: this is a live visuals tool. Nothing on the per-frame path should allocate or recompile needlessly
- **UI copy**: lowercase, short, in the voice of the HYDRACTRL site (`// comments` for descriptions). The landing page speaks to people who don't code: plain words, no jargon, nothing that assumes they know hydra
